## 2. Main Performance Problems

The previous investigation identified these potential bottlenecks:

1. Insufficient RAM while running Windows, Ollama, FastAPI, Next.js and the browser simultaneously.
2. CPU-based LLM inference instead of dedicated GPU inference.
3. MultiQueryRetriever generates alternative queries using an additional LLM call before retrieval.
4. BM25/hybrid retrieval appears to scan the vector collection unnecessarily and may fail because EnsembleRetriever is unavailable.
5. Too many document chunks are retrieved for each question.
6. The context window is currently 4096.
7. Next.js development mode consumes additional memory and causes compilation delays.
8. Model loading and unloading may increase response times.
9. PDF extraction or embedding generation may be repeated unnecessarily.

Investigate each issue independently. Do not assume every suspected issue is necessarily present in the current code.

# 3. Phase 1: Optimize the Existing RAG Pipeline

This phase is the highest priority.

### A. Remove unnecessary MultiQueryRetriever processing

- Inspect the current retriever implementation.
- If MultiQueryRetriever is being used, replace it with a direct vector retriever.
- Avoid making an additional LLM call just to generate alternative search queries.
- Retrieve relevant document chunks directly using the user's original question.
- Preserve source-document metadata and page references.
- Ensure that answers remain grounded in the uploaded PDF.

### B. Optimize document retrieval

Reduce the default retrieval count.

Current configuration:
- Retrieval chunks: 10

Target configuration:
- Retrieval chunks: 4

Make this configurable through environment variables rather than hardcoding values throughout the project.

For example:

`RETRIEVAL_MAX_CHUNKS=4`

Do not blindly reduce the number of chunks if testing demonstrates that relevant information is being missed. Compare retrieval quality before and after the modification.

### C. Disable unnecessary hybrid search

Inspect the BM25/hybrid search implementation.

If BM25 is broken, unavailable, or providing no measurable improvement:

- Disable hybrid search.
- Use the existing vector retriever.
- Avoid scanning the entire vector database on every question.
- Remove unnecessary initialization or computation.

Use:

`ENABLE_HYBRID_SEARCH=False`

Preserve the option to enable hybrid search later if it is fixed and proven useful.

### D. Optimize Ollama generation settings

Use a smaller context window.

Target:

- `num_ctx = 2048`
- `num_predict = 512`

Inspect the existing ChatOllama configuration and apply the settings using the correct supported API for the installed library versions.

Do not introduce incompatible parameters.

Also:
- Avoid excessively long system prompts.
- Remove redundant instructions.
- Keep answers concise but informative.
- Preserve citations and source references.
- Avoid generating unnecessary text.

### E. Limit Ollama parallel processing

Configure:

`OLLAMA_NUM_PARALLEL=1`

Consider:

`OLLAMA_MAX_LOADED_MODELS=1`

However, test the effects on model switching and embedding generation. Do not blindly introduce settings that cause frequent model unloading and reloading.

The objective is to prevent unnecessary memory consumption while maintaining reasonable response speed.

# 5. Phase 3: Optimize PDF Processing and Embeddings

Inspect the complete document ingestion workflow.

The PDF should not be repeatedly extracted, split and embedded whenever a user asks a question.

Implement or verify the following workflow:

### One-time processing during upload

1. Upload PDF.
2. Extract PDF text.
3. Split text into appropriate chunks.
4. Generate embeddings.
5. Store embeddings in the vector database.
6. Preserve document metadata, page numbers and source information.

### Processing during subsequent questions

1. Accept the user's question.
2. Generate an embedding for the question.
3. Retrieve relevant document chunks.
4. Construct a concise context.
5. Pass the context and question to the LLM.
6. Generate a grounded answer with citations.

### Additional requirements

- Reuse existing embeddings.
- Avoid unnecessary re-indexing.
- Persist the vector database.
- Avoid loading the complete PDF into memory for every question.
- Prevent duplicate document indexing.
- Handle multiple PDF uploads correctly.
- Preserve existing PDF upload functionality.

Do not change the vector database technology unless there is a clear technical reason.
